# Review output format

Write the full review to `out/REVIEW.md` (PR mode also `out/PR_COMMENT.md`). Keep the structure below; drop empty severity
sections. Emoji: 🔴 Critical · 🟠 High · 🟡 Medium · 🔵 Low · ⚪ Nit.

## judgment.json (write before scoring)

Your own findings (and any static finding you **re-graded or dropped**) go into `out/judgment.json` as a list using the
static schema, so the score is computed by script, not estimated:

```json
[
  {"id": "DAX101", "category": "DAX", "severity": "high", "object": "Sales[Total Revenue]",
   "file": "Model.SemanticModel/definition/tables/Sales.tmdl", "line": 16,
   "message": "...", "evidence": "measure 'Total Revenue' = COUNTROWS(Sales)", "fix": "..."},
  {"id": "MOD006", "category": "Model", "severity": "low", "object": "Customer", "dropped": true,
   "reason": "dimension code is a business identifier users search by"}
]
```

`dropped: true` entries are ignored by scoring. For a re-graded static finding, add a `dropped: true` copy of the
original plus the new entry. Then run:

```
python3 <scripts>/static_checks.py --rescore out/findings.json out/judgment.json
```

and use `overall` / `byCategory` from its output. Categories with `null` (e.g. no report) are shown as "n/a".

## REVIEW.md

```markdown
# Power BI review: <project name>

**Health score: <overall>/100** · <mode: Full review | PR #<n> (<base>…<head>)> · <date>

| Model | DAX | Power Query | Report | Security | Governance |
|:-:|:-:|:-:|:-:|:-:|:-:|
| <score> | <score> | <score> | <score or n/a> | <score> | <score> |

<1–2 sentence verdict in plain language, the way a senior colleague would say it.>

## Fix these first
1. **<title>** · `<file>:<line>` · <one line: what breaks if you do not>
2. …
3. …

## Findings

### 🔴 Critical
#### <ID> · <title>
**Where:** `<file>:<line>` · <object>
```<lang>
<quoted code from that line, exactly as in the file (secrets masked)>
```
**Why it matters:** <1–2 sentences, specific to this model.>
**Fix:**
```<dax|tmdl|m>
<ready-to-paste replacement>
```

### 🟠 High
…

### 🟡 Medium
…

### 🔵 Low
<compact: one bullet per finding: **ID title** · `file:line` · why · fix in one line or a short snippet>

### ⚪ Nit
<compact bullets>

## What's good
- <2–4 concrete things done well, with a file reference where possible>

## Notes
- <limits of this review: legacy report format, no report found, thin reports elsewhere, rules disabled, etc.>
- Static checks: <n> findings, <m> confirmed, <k> dropped as not applicable.
```

Ordering inside a severity: by impact on correctness first (wrong numbers, data exposure), then performance, then
maintainability. Group findings with the same root cause (e.g. five visible keys → one finding listing all five).

## PR_COMMENT.md (PR mode)

GitHub-ready markdown, shorter than REVIEW.md, only about objects in `scopeKeys`:

```markdown
## 🧑‍💼 Power BI review · <score>/100 for the changed objects

**<verdict sentence>** · <N> findings on this PR (<counts by severity>)

| | Finding | Where |
|---|---|---|
| 🔴 | **PR001** Visual still uses removed `Customer[Segment]` | `…/customerTable/visual.json:13` |
| 🟠 | **DAX106** `[Margin]` now divides instead of subtracts; feeds `[Margin %]` and 3 visuals | `…/_Measures.tmdl:18` |

<details><summary>Details and fixes</summary>

<same per-finding blocks as REVIEW.md for Critical/High/Medium; Low/Nit as bullets>

</details>

<sub>Generated by powerbi-senior-reviewer · static checks + reviewer judgment · nothing left this machine</sub>
```

For line-level comments (only if the user asks to post them), each comment = one finding, anchored to a line inside
`changedLines` for that file; findings on unchanged lines go into the summary comment instead.

## Chat summary (after writing the files)

5–8 lines: score, the top 3, counts by severity, where the files are, and one offer ("Want me to fix #1?").
